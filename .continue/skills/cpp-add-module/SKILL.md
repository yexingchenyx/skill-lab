# Add C++ Module

Add a new module to an existing C++ project that was generated by the
`cpp-create-project` skill (modular `src/<module>/` layout, aggregate
`${PROJECT_NAME}_lib` target, `tests/<module>/` per-module tests).

## When to use
- User asks to add a module to a cpp-create-project project

## Inputs to ask user (if not specified)
- Module name (required, e.g. `storage`)
- Does the module depend on `core`? (default: **yes**)

## Steps

1. Create the module directory with a sample `foo` unit (rename to fit the
   user's use case):

```
src/<module-name>/
├── CMakeLists.txt
├── include/<project-name>/<module-name>/
│   └── foo.hpp
└── src/
    └── foo.cpp
tests/<module-name>/
├── CMakeLists.txt
└── foo_test.cpp
```

2. Generate files from the `cpp-create-project` skill's templates
   (replace placeholders: `<project-name>`, `<PROJECT_NAME_UPPER>`,
   `<module-name>`, `<MODULE_NAME_UPPER>`; create destination directories
   with `mkdir -p` first — plain `cp` does not create parent directories):

- Depends on `core` (default; links `${PROJECT_NAME}::core` PUBLIC):
  - `templates/module-deps-CMakeLists.txt.tmpl` → `src/<module-name>/CMakeLists.txt`
- No module dependencies (only if the user explicitly declines core):
  - `templates/module-CMakeLists.txt.tmpl` → `src/<module-name>/CMakeLists.txt`
- Header/impl (adjust the sample `Greeter` to the module's purpose):
  - `templates/module-foo-header.hpp.tmpl` →
    `src/<module-name>/include/<project-name>/<module-name>/foo.hpp`
    (change the namespace segment `core` → `<module-name>`)
  - `templates/module-foo-impl.cpp.tmpl` → `src/<module-name>/src/foo.cpp`
- Tests:
  - `templates/test-module-CMakeLists.txt.tmpl` →
    `tests/<module-name>/CMakeLists.txt`
  - `templates/test-core-foo.cpp.tmpl` → `tests/<module-name>/foo_test.cpp`
    (change the namespace segment and test content to match the module)

3. Wire the module in (two edits each):

- `src/CMakeLists.txt`: add `add_subdirectory(<module-name>)`
- Top-level `CMakeLists.txt`: in the `${PROJECT_NAME}_lib` INTERFACE target's
  `target_link_libraries`, add `${PROJECT_NAME}::<module-name>`
  (the namespaced alias, e.g. after `${PROJECT_NAME}::algorithm`).

4. Verify (if the user wants a build):

```bash
cmake --preset release && cmake --build --preset release && ctest --preset release
```

## Built-in conventions (already in the templates — do not re-implement)
- The module CMakeLists templates emit a plain
  `add_library(${PROJECT_NAME}_<module> ...)` — the lib type (shared/static)
  is controlled by `BUILD_SHARED_LIBS` from the presets, and
  `<PROJECT_NAME_UPPER>_STATIC_DEFINE` is set PUBLIC automatically when
  building static — no manual export-macro wiring is needed.
- Headers already mark exported symbols with `<PROJECT_NAME_UPPER>_API`
  (the single unified macro from the generated `config.h`); new modules
  need **no** `config.h` changes.
- Namespaces use `<PROJECT_NAME_UPPER>_NS` (defined in the generated
  `config.h`; expands from `<PROJECT_NAME_UPPER>_NAMESPACE`, default =
  project name).
- `vcpkg.json` / `vcpkg-configuration.json` are **not** affected by adding
  a module (only third-party libraries are, via `cpp-add-thirdparty`).
- The presets already wire the vcpkg toolchain (`options.cmake` sets
  `CMAKE_TOOLCHAIN_FILE` before `project()`) and the shared/static switch
  (`BUILD_SHARED_LIBS`) — no extra configure flags.

## Notes
- Header path convention: `#include "<project-name>/<module-name>/<header>.hpp"`.
- Namespace: `namespace <PROJECT_NAME_UPPER>_NS::<module-name> { ... }`.
- If the module depends on other modules, link them in its CMakeLists.txt
  via the namespaced aliases (`${PROJECT_NAME}::<module>`, PUBLIC).
- Do not initialize git or commit unless the user asks.
